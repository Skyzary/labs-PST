## **Вариант 1**

### Питання 1

**Динамічна типізація в Ruby**
Це означає, що типи перевіряються під час виконання програми (в рантаймі), а не при компіляції. У Ruby типи мають **самі об'єкти**, а **змінні — ні**. Змінна це просто посилання (ярлик) на об'єкт у пам'яті. Тому в одну і ту ж змінну можна спочатку записати число, а потім рядок — сам об'єкт знає свій клас і які методи він підтримує.

**Переприсвоєння змінної vs мутація об'єкта**

- **Переприсвоєння** (`a = "новий текст"`) — ми беремо змінну і змушуємо її вказувати на інший об'єкт у пам'яті. Старий об'єкт при цьому не змінюється.
- **Мутація** (`a.upcase!` або `a << "!"`) — ми змінюємо внутрішній стан того самого об'єкта за старою адресою в пам'яті.

Коли ми пишемо `b = a`, нова копія об'єкта не створюється (Ruby не робить зайвої роботи з пам'яттю). Обидві змінні просто починають посилатися на один і той самий об'єкт. Це призводить до неочевидних багів: якщо ти передав масив або рядок у метод, а там його змінили мутуючим методом (з `!` або `[]=`), він зміниться і в усіх інших місцях програми, де на нього є посилання.

**Різниця між `==` та `equal?`**

- `==` перевіряє **еквівалентність значень** (наприклад, два різні рядки `"привіт" == "привіт"` повернуть `true`, бо їхній вміст однаковий). Цей метод часто перевизначають у власних класах.
- `equal?` перевіряє **ідентичність об'єктів** — чи вказують дві змінні на один і той самий об'єкт у пам'яті (чи однаковий у них `object_id`). Для двох різних екземплярів `"привіт".equal?("привіт")` поверне `false`. Його не прийнято перевизначати.

### Питання 2

**Gem, RubyGems та Bundler**

- **Gem** — це просто пакет (бібліотека) з готовим кодом на Ruby, який можна підключити до свого проєкту, щоб не писати велосипеди.
- **RubyGems** — це стандартний менеджер пакетів у Ruby (щось типу `pip` у Python). Він вміє завантажувати, встановлювати і видаляти геми в систему, але не дуже добре розрулює конфлікти версій між різними проєктами.
- **Bundler** — це інструмент, який керує залежностями конкретного проєкту. Він гарантує, що у всіх розробників і на сервері будуть встановлені абсолютно однакові версії всіх гемів.

**Gemfile, Gemfile.lock, `~>` та `bundle exec`**

- **Gemfile** — файл, де ми руками пишемо, які геми потрібні проєкту та які приблизно версії підходять.
- **Gemfile.lock** — файл, який Bundler генерує автоматично. Там зафіксовані точні версії всіх гемів (включно з їхніми підзалежностями) на момент встановлення.
- **У Git зберігають обидва файли.** `Gemfile` потрібен, щоб бачити прямі залежності проєкту, а `Gemfile.lock` — щоб кожен, хто склонує репозиторій, отримав ідентичне середовище, і нічого не зламалося через випадкове оновлення якоїсь бібліотеки.
- **Оператор `~>` (песимістичний оператор)** дозволяє оновлювати тільки останню цифру у вказаній версії. Наприклад, `~> 1.4.2` означає `>= 1.4.2`, але `< 1.5.0` (можна ставити патчі `1.4.3`, `1.4.9`, але не мінорну версію `1.5.0`, де вже можуть зламати зворотну сумісність).
- **`bundle exec`** запускає скрипт у контексті саме тих версій гемів, які прописані в `Gemfile.lock`. Без нього Ruby може підтягнути новішу або старішу версію гема, яка просто стоїть глобально в системі, і програма впаде.

### Питання 3

**Шлях даних та типові помилки**

1. **Файл на диску** (відкриття і читання файлу):
   - _Помилки файлової системи:_ файлу не існує, немає прав на читання, передали папку замість файлу.
   - _Винятки:_ `Errno::ENOENT`, `Errno::EACCES`, `Errno::EISDIR` (усі наслідуються від `SystemCallError` / `IOError`).
2. **Текст → Структури Ruby** (парсинг, наприклад, JSON або CSV):
   - _Помилки синтаксису формату:_ битий файл, незакрита дужка, зайва кома, невалідне кодування.
   - _Винятки:_ `JSON::ParserError`, `CSV::MalformedCSVError`, `Psych::SyntaxError` (для YAML), `EncodingError`.
3. **Структури Ruby → Перевірка** (бізнес-логіка / валідація):
   - _Помилки предметних правил:_ синтаксис файлу правильний, але відсутнє обов'язкове поле, вік від'ємний або формат email кривий.
   - _Винятки:_ стандартні `ArgumentError`, `KeyError` (якщо використовуємо `hash.fetch`), `TypeError`, або власні кастомні класи помилок (наприклад, `ValidationError < StandardError`).
4. **Результат** (вивід або збереження оброблених даних).

**Де обробляти помилки і чому не варто робити `puts` + `exit` у нижчих методах**
Обробляти винятки потрібно **на верхньому рівні програми** (у точці входу: в CLI-контролері, в `main` або на рівні HTTP-контролера у веб-додатку).

Нижні методи (які парсять файл або рахують бізнес-логіку) повинні просто кидати виняток (`raise`), а не друкувати щось у консоль і викликати `exit`. Якщо метод викликає `exit`, він вбиває весь процес: ти не зможеш нормально протестувати цей метод (тести просто впадуть), не зможеш перевикористати його у веб-інтерфейсі (де замість `exit` треба віддати HTTP 400/500) і не даєш коду зверху шансу самому вирішити, що робити з помилкою (наприклад, спробувати відкрити резервний файл).

**Чому `rescue []` або `rescue {}` — погана практика**
По-перше, конструкція без вказання класу помилки перехоплює будь-який `StandardError` — навіть твої власні одруківки в коді (наприклад, `NoMethodError` чи `NameError`). По-друге, ти мовчки ховаєш проблему: програма замість того, щоб впасти і показати, що файл пошкоджений або не знайдений, робить вигляд, що даних просто немає. Це призводить до тихих логічних багів далі по коду (наприклад, система вирішить, що список боржників порожній, хоча насправді просто впав парсер), і знайти причину такої поведінки потім дуже важко.

### Практична задача

**`data/students.csv`**

```csv
name,score
Олена,87
Тарас,45
Ірина,abc
Петро,
Марія,60
```

**`report.rb`**

```ruby
# frozen_string_literal: true

require "csv"
require "fileutils"
require "json"

PASSING_SCORE = 60
VALID_SCORE_RANGE = (0..100)

def parse_score(raw_score)
  raise ArgumentError, "Missing score" if raw_score.nil?

  stripped = raw_score.strip
  raise ArgumentError, "Empty score" if stripped.empty?

  score = Integer(stripped, 10)
  unless VALID_SCORE_RANGE.cover?(score)
    raise ArgumentError, "Score out of range: #{score}"
  end

  score
end

def build_report(csv_path)
  total = 0
  valid_scores = []
  invalid_rows = []

  CSV.foreach(csv_path, headers: true, encoding: "UTF-8").with_index(1) do |row, row_number|
    total += 1
    begin
      score = parse_score(row["score"])
      valid_scores << score
    rescue ArgumentError, TypeError
      invalid_rows << row_number
    end
  end

  valid_count = valid_scores.size
  average = valid_count.zero? ? 0.0 : (valid_scores.sum.to_f / valid_count).round(1)
  passed = valid_scores.count { |score| score >= PASSING_SCORE }

  {
    total: total,
    valid: valid_count,
    invalid_rows: invalid_rows,
    average: average,
    passed: passed
  }
end

def write_report(output_path, report)
  FileUtils.mkdir_p(File.dirname(output_path))
  File.write(output_path, "#{JSON.pretty_generate(report)}\n", encoding: "UTF-8")
end

def main
  csv_path = File.join(__dir__, "data", "students.csv")
  output_path = File.join(__dir__, "output", "report.json")

  report = build_report(csv_path)
  write_report(output_path, report)
rescue Errno::ENOENT => e
  warn "Помилка: файл не знайдено (#{e.message})"
  exit 1
rescue CSV::MalformedCSVError => e
  warn "Помилка формату CSV: #{e.message}"
  exit 1
end

main if __FILE__ == $PROGRAM_NAME
```
